InsightAI Architecture

System architecture reference

How InsightAI is put together

InsightAI is a full-stack AI data-intelligence platform: natural-language SQL and dashboards on one side, an end-to-end data-science workspace — profiling, cleaning, EDA and real model training — on the other. This document walks the whole system: the layers, the request paths, the databases, and the decisions that hold it together.

01What it is

InsightAI began as QueryMind, an AI business-intelligence tool. The data-science workspace was added on top without rewriting the original — both halves share one backend, one frontend, one auth layer.

The two halves

The BI half. You connect a PostgreSQL database and ask a question in plain English. A tool-calling LangGraph agent explores your schema, writes SQL, validates it, runs it read-only, and returns the answer with an explanation, a results table, and an auto-chosen chart. Results can be pinned to drag-and-drop dashboards or saved to a query library and scheduled.

The Data Science half — Insight Studio. Take any query result, upload a CSV / TSV / XLSX, pick a database table, or load the demo dataset, then step through a guided workflow: Dataset → Quality → Clean → Explore → ML → Report. It profiles the data, scores its quality, recommends cleaning operations, runs EDA, and trains and compares real scikit-learn models — with an Ask InsightAI panel that answers questions grounded in what was actually computed.

The load-bearing principle Every number a user sees — a mean, a quality score, an F1, a feature importance, a row count — is computed in Python with pandas / numpy / scikit-learn / DuckDB. The LLM is an orchestrator and explanation layer: it decides what to do and puts computed results into words. It never calculates a statistic and never invents a figure. Diagrams in this document mark the deterministic path in violet.

03System overview

Five tiers. The browser talks only to the FastAPI layer; everything below it — agents, the query engine, the data-science engine, repositories, workers — is orchestrated by a thin service layer.

Backend package layout

Everything lives under backend/app/, split by responsibility rather than by feature:

api/v1
Route modules, Pydantic request/response schemas, shared dependencies (CurrentUserDep, rate limiting).
services/
~35 modules that orchestrate a request — chat_service, connection_service, dashboard_service, data_science_service, … Held as module-level singletons wired through container.py.
agents/
db_agent (the tool-calling loop), nl_to_sql (the fallback graph), visualization, dashboard_planner, insights. Prompts are markdown files next to the code.
data_science/
The deterministic DS engine — dataset, profiling, quality, cleaning, eda, ml, nl_query, report, demo_data, and insights_llm (the only LLM-touching module).
query_engine/
executor, safety, schema_inspector, connection_pool, connection_scope, TLS handling.
db/
SQLAlchemy ORM models, owner-scoped repositories, session helpers; Alembic migrations sit in backend/alembic/versions.
integrations/
llm_client (the provider abstraction + metering) and the Supabase auth adapter.
workers/
The Celery app, Beat schedule, and one module per job type.
core/
Config, secrets, logging, CORS, error handling, metrics.

04A chat request, end to end

The single most important path in the BI half. It shows how the agent, the query engine, and the visualisation step connect.

  1. Guard. chat_input_guard rejects messages that contain credentials or ask for INSERT/UPDATE/DELETE/DROP.
  2. Ground. chat_intent_orchestrator loads the connection's cached schema catalog and any semantic definitions, and assembles conversation history and prior-result context.
  3. Agent loop. The LangGraph agent iterates think → call tool → observe, exploring schema and validating SQL, under a tool-call budget and a wall-clock budget.
  4. Execute. Proposed SQL goes through the query engine — re-validated, wrapped read-only, given a statement timeout and a row limit — then run against the connected database.
  5. Visualise. The visualization agent inspects the result columns and picks a chart type.
  6. Persist & stream. The message, SQL, rows, chart spec and full agent trace are saved to the app database; progress and the final answer stream to the browser over a Redis-backed run-event stream (or a Celery worker runs the whole loop when streaming is enabled).

When the agent fails — budget exhausted, invalid output, repeated tool errors — a simpler nl_to_sql LangGraph pipeline takes over (schema-prompted generation → validate → execute → one error-correction retry), and the failed agent trace is kept for debugging.

06Query engine & SQL safety

Every statement that reaches a connected database goes through one function, and defense is layered so no single check is load-bearing.

  • Write-intent detection at the chat boundary rejects mutation requests before any model call.
  • Static validation parses the SQL (sqlglot) and rejects non-SELECT statements, multiple statements, and dangerous constructs.
  • Transaction-level read-only. On PostgreSQL the executor issues SET TRANSACTION READ ONLY and rolls back at the end — the database itself refuses writes even if a check were bypassed.
  • Statement timeout (SET statement_timeout) and an automatic row-limit wrap bound every result.
  • Connection scope. A connection can be restricted to named schemas/tables; queries referencing anything outside the scope are rejected (connection_scope).
  • Credential encryption. Connected-database passwords are encrypted with a Fernet key before they touch the app database; TLS material is written to a locked-down temp dir.
  • Pooling. One SQLAlchemy engine is cached per connection; schema introspection is cached and invalidated on drift (a “table not found” error triggers a refresh + “did you mean” suggestion).

07Insight Studio: the data-science engine

A guided pipeline over a bounded, in-memory analysis copy of a dataset. The source database is only ever read.

Module by module

dataset.py
Wraps a DataFrame with provenance and the single source of truth for column kind (numeric / categorical / datetime / boolean / text). Caps the analysis copy at 50k rows.
profiling.py
Dataset- and column-level statistics — missing %, unique %, quantiles, IQR, outlier counts, skew, histograms. Pure pandas/numpy.
quality.py
Seven issue detectors (missing values, duplicates, numeric/date-as-string, categorical inconsistency, outliers, constant columns, potential target leakage) and a deterministic 0–100 quality score: each of seven dimensions starts at 100 and loses points per issue by severity.
cleaning.py
Eleven operations (trim, standardise categories, to-numeric, to-datetime, drop duplicates/column/rows, impute with mean/median/mode/constant/KNN, handle outliers, group rare categories, map categories). A recommendation engine turns each quality issue into an operation with problem / solution / reason / expected impact. Dry-run preview + exact-snapshot undo/redo.
eda.py
Numeric and categorical summaries, correlation matrix, seven chart specs, and auto-insights whose every figure is lifted from the computed stats (“associated with”, never “causes”).
ml.py
Task auto-detection; a scikit-learn Pipeline + ColumnTransformer fitted only on the training split; 5 classifiers / 6 regressors; stratified split; cross-validation; model comparison ranked by the task-appropriate metric; native or permutation feature importance collapsed to source columns; a prediction that runs inputs back through the exact fitted pipeline; joblib export.
nl_query.py
Natural-language querying of the dataset via DuckDB — see §8.
report.py
Assembles the computed artifacts into an executive summary plus sections; exported as standalone HTML from the UI.
insights_llm.py
The only module that calls the LLM. Wraps every call so the feature degrades to a deterministic fallback if the model or a credential is unavailable.
Deliberate trade-off Analysis sessions live in process memory — bounded (8 per user, 3-hour TTL), owner-scoped, never persisted, never written back to a database. They don't survive a restart and aren't shared across worker processes. This fits the synchronous single-analyst workflow and keeps the source data untouched; the alternative (a per-user scratch database) was more infrastructure than the feature warranted.

The service layer (data_science_service.py) owns the session store and orchestration; the routes under /api/data-science/* are all owner-scoped through CurrentUserDep and run as sync handlers in the threadpool because the ML work is CPU-bound.

09The LLM layer

One abstraction, several providers, per-user credential policy, and a firm rule about what the model is allowed to do.

  • Provider abstraction. integrations/llm_client.py exposes get_chat_llm() and invoke_chat_llm() over Gemini (default), Groq and OpenAI. Switching is one env var (LLM_PROVIDER). Response content is normalised through content_to_text() — Gemini 3.x returns a list of content blocks with thought signatures, not a string.
  • Credential modes. LLM_CREDENTIAL_MODE is deployment (use the app's key, unmetered), hybrid (app key with a per-user trial limit, then bring-your-own), or byok_required. User keys are stored encrypted and validated on save.
  • Metering. Every call is wrapped as a metered invocation that records provider, model, token counts, latency and outcome, and maps provider errors to typed application errors (401→credential_invalid, 429→rate_limited, 5xx→provider_unavailable).
  • Grounding. In Insight Studio the system prompt is explicit: “Use ONLY numbers present in the payload — never invent or recompute figures. Say ‘associated with’, not ‘causes’.” Every call has a deterministic fallback, so a provider outage never breaks a page.
  • Where the LLM is used: the chat agent loop and its fallback pipeline; chart-type selection; dashboard planning; per-widget insights; question-suggestion generation; semantic-definition suggestions; and, in Insight Studio, cleaning-recommendation narration, EDA and model narratives, Ask InsightAI, and NL→SQL for uploads.

10Where data lives

Four distinct homes for state, with very different lifetimes and trust levels.

In the zero-setup dev stack a fifth database appears: insightai_demo, a ~33-table demo schema (e-commerce / HR / projects / support) seeded on first boot and auto-registered as a connection, so Chat, Dashboards, Library and Analytics have real data without any external account.

11Frontend architecture

A React 19 single-page app. Ten routes, feature-grouped components, a thin service layer over fetch.

Routing
react-router-dom v7. Public: / (landing), /auth, /s/:token (shared dashboard). Protected: /chat, /dashboard, /analytics, /library, /connections, /settings, /upgrade, and /insight-studio. A ProtectedRoute wrapper redirects to /auth once auth is resolved and no user is present.
Auth
AuthContext exposes user, loading, isDevMode. In dev mode it short-circuits to a mock user and never calls the auth API.
State
Zustand for the few pieces of cross-component state: settingsStore, and insightStudioStore which carries the “Analyze Dataset” hand-off from a chat result (persisted to sessionStorage so it survives the navigation). Everything else is local component state.
Services
services/http.ts wraps fetch with cookie credentials and a one-shot 401→refresh→retry. services/api.ts is the typed BI API; services/dataScience.ts is the Insight Studio API, including a binary fetch for the model download.
Components
Grouped by area: chat/, dashboard/, charts/, connections/, library/, analytics/, settings/, landing/, insight-studio/, plus common/ shell components.
Insight Studio
One page with a six-step nav (StepNav) and per-step panels (DatasetStep … ReportStep), a Recharts-based DsChart renderer for the EDA chart specs, an AskPanel, a TableSourcePicker, and a PinToDashboardButton that reuses the existing dashboard-widget API.
Design system
A token file (components/dashboard/tokens.ts) — warm editorial palette, Playfair Display headings, DM Mono labels, Inter body — applied via inline styles.

13Authentication

Supabase JWT in production; a mock-auth mode for local development.

  • Production. Supabase issues the JWT; the frontend stores it in an HTTP-only cookie. Every protected route depends on get_current_user, which verifies the token (HS256 secret or an EC P-256 JWK), checks a local session-revocation table, and confirms the user is active.
  • Dev mode. With BACKEND_DEV_MODE=true and no SUPABASE_JWT_SECRET, mock_auth_enabled turns on: any request with no token (or the literal dev-token) resolves to a fixed dev user 00000000-…-0000. The frontend's VITE_DEV_MODE=true matches this and skips the login screen.
  • Owner scoping. Every repository filters by owner_id at the data layer; Insight Studio's session store checks session.user_id on every access. The app database also carries Postgres row-level-security policies keyed on auth.uid().
  • Config refuses to start with BACKEND_DEV_MODE enabled when APP_ENV is production.

14Running it

Two Compose files. The production one needs a Supabase project and an LLM key; the dev overlay needs nothing.

The stack (8 services)

redis
Broker, run-event streams, caches.
backend
FastAPI + Uvicorn. Runs alembic upgrade head on start, then serves :8000.
worker / agent-worker / dashboard-worker
Three Celery pools bound to the queues in §12.
beat
Celery Beat scheduler.
frontend
Vite build served by nginx on :5173.
db (dev only)
A throwaway PostgreSQL. Two init scripts run once on a fresh volume: 00-supabase-shim.sql stubs the auth schema and auth.uid() so the Supabase-flavoured migrations apply on vanilla Postgres, and 10-load-demo-db.sh creates and seeds insightai_demo.
Zero-setup dev stack docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build — local Postgres, local Redis, mock auth, demo data auto-connected. A gitignored backend/.env.dev.local is loaded as an optional second env file for a real GEMINI_API_KEY, so the key never lands in a committed file. Open http://localhost:5173 and you're the dev user immediately.

17Design decisions

The calls that shaped the codebase, and why.

Extend, don't rewrite

The data-science workspace was added alongside the BI platform. Same FastAPI app, same service/repository pattern, same auth, same React shell, same chart components. The chat agent, dashboards, query library and scheduling are untouched. This kept the diff reviewable and meant no existing capability regressed.

Deterministic core, LLM as narrator

Statistics, quality scores, cleaning impact, model metrics and feature importance are computed in Python and only then handed to the model to explain. This removes the entire class of hallucinated-analytics failures, makes results reproducible and testable, and lets every AI feature degrade to a still-accurate fallback when a provider is down.

Read-only, everywhere, in layers

A connected database is untrusted input. Write-intent is refused at the chat boundary, SQL is statically validated, the transaction is set read-only, and the connection can be scoped to specific tables. The DuckDB path for uploads is sandboxed the same way — external access off and a SELECT-only validator. No single check is trusted alone.

Ephemeral analysis sessions

Insight Studio holds working data in memory rather than in a scratch database. The cost is that sessions don't survive a restart and aren't shared across workers; the benefit is zero new persistence infrastructure and a guarantee that the source data is never copied into a store. For a synchronous single-analyst workflow that was the right trade.

One provider abstraction

Gemini, Groq and OpenAI sit behind a single metered client. Switching is an env var; per-user credential policy (deployment key, hybrid trial, or bring-your-own) is enforced in one place; provider-specific response shapes and error codes are normalised once.
